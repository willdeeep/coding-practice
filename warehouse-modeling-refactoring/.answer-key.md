# Answer key — `warehouse.py`

Not for the user to read before completing their own critique
(`AGENTS.md` Checkpoints 1–5, same convention as `sequence-refactoring-abc`
and `orders-etl-refactoring`). For the assistant's use during Gotchas /
Missed-issues / Final-feedback only.

Categories: `duplication` (design smell), `performance`, `correctness`
(bug), `gotcha` (technically works, indefensible). Tiers: Critical /
Worthwhile / Stylistic.

---

## 1. Hardcoded Snowflake credentials (`SNOWFLAKE_CONN`)

- **Category:** gotcha (security).
- **Tier:** Critical. Even though this script doesn't actually connect
  to Snowflake with it, the constant is written exactly the way it would
  be if it did — a plaintext password sitting in source. Directly maps to
  the job spec's "Snowflake... security/access controls" line. Should
  come from environment/secrets-manager, never committed to source.

## 2. `sales_flat` — a single denormalized table, no star schema

- **Category:** duplication / data-modeling design smell.
- **Tier:** Critical — this is the headline issue, and maps directly to
  "data modelling and data warehousing principles" in the job spec.
  Customer and product attributes are repeated on every sale row instead
  of living in `dim_customer`/`dim_product` tables joined to a
  `fact_sales` table. Costs storage, and — worse — costs correctness: if
  `Customer 50`'s region changes, every historical row needs updating, or
  historical and current region silently diverge. Watch for whether the
  candidate names "star schema" / "fact and dimension tables" specifically,
  not just "this table has too many columns."

## 3. Non-sargable `WHERE` clause in `top_customers_by_region`

- **Where:** `WHERE UPPER(customer_region) = UPPER(?) AND
  substr(sale_date, 1, 4) = ?`
- **Category:** performance.
- **Tier:** Critical. Wrapping a column in a function (`UPPER(...)`,
  `substr(...)`) means no index on that column could ever be used, even
  if one existed — the engine must evaluate the function on every row.
  Verified: `EXPLAIN QUERY PLAN` on this exact query returns `SCAN
  sales_flat` (a full table scan), not `SEARCH`. The fix is a case-
  normalized column (or store region consistently) and a real date range
  (`sale_date >= '2025-01-01' AND sale_date < '2026-01-01'`) rather than
  string-slicing the year out.

## 4. No indexes anywhere in the warehouse

- **Category:** performance.
- **Tier:** Worthwhile, tightly coupled to #3 — even after fixing the
  predicate shape, there's no index on `customer_region` or `sale_date`
  to actually use. Both need fixing together; fixing only the predicate
  shape without adding the index leaves you with a correctly-shaped query
  still doing a full scan.

## 5. N+1 query pattern in `customer_lifetime_value`

- **Where:** the `for customer_id in customer_ids:` loop, one `execute`
  per id.
- **Category:** performance.
- **Tier:** Critical — same family of issue as the "new connection per
  row" lesson from `orders-etl-refactoring`, one level up: this is one
  *query round-trip* per customer instead of one query total. Fix:
  `WHERE customer_id IN (...)` with `GROUP BY customer_id`, one execute.
  Worth watching whether the candidate names this "N+1" specifically —
  it's standard vocabulary for exactly this shape of problem, heavily
  associated with ORMs but just as real in hand-written SQL loops.

## 6. `net_revenue_by_product` — join fan-out, wrong numbers silently

- **Where:** `JOIN refunds r ON r.product_id = s.product_id`.
- **Category:** correctness (gotcha — produces plausible-looking numbers
  that are simply wrong).
- **Tier:** Critical, arguably the most important single finding in this
  exercise. `refunds` has no link to a specific sale (no `sale_id`), only
  `product_id` — so joining raw rows on `product_id` produces every
  (sale, refund) *pair* for that product, not a meaningful per-sale
  correspondence. Verified concretely: for product 1, true gross revenue
  is `101,309.46` and true total refunds `4,824.26` (124 sales, 13
  refunds) — but the query reports `1,317,022.98` and `598,208.24`,
  inflated by exactly ×13 and ×124 respectively (each side multiplied by
  the *other* side's row count). The fix isn't a different join
  condition — there isn't a correct one available with these keys. The
  fix is aggregating each side independently first (`SUM` per product in
  a subquery/CTE on each side) and combining the two aggregates, never
  joining the raw fact rows. This is the general lesson: **join before
  aggregating** is only safe on a one-to-one or one-to-many key; anything
  else needs aggregate-then-combine.

## 7. Full rebuild every run, no incremental load

- **Where:** `rebuild_warehouse` — `DROP TABLE IF EXISTS` then regenerates
  everything from scratch.
- **Category:** design/architecture smell.
- **Tier:** Worthwhile. Fine at 5,000 rows; doesn't scale, and maps
  directly to "dbt... deployment best practices" (incremental models) in
  the job spec. Worth noting as a legitimate trade-off rather than an
  outright bug: full-refresh is *also* trivially idempotent (a bonus a
  candidate might raise) — the real question is where that trade-off
  stops being worth it as volume grows, not that full-refresh is simply
  wrong.

## Lower-tier / stylistic (present, not the point of the exercise)

- No indexes/constraints declared for any table (partially covered above,
  but also: no primary keys at all).
- `print` instead of `logging`.
- No `.gitignore`d secrets pattern shown (not applicable here, but worth
  a candidate raising it given #1).

Don't expect a candidate to raise every stylistic item — useful if they
come up organically, not omissions worth penalising.
