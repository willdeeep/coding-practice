# Answer key — `etl.py`

Not for the user to read before they've completed their own critique
(Checkpoints 1–5 in `AGENTS.md`). For the assistant's use during the
Gotchas / Missed-issues / Final-feedback steps only.

Categories: `duplication` (design smell), `performance`, `correctness`
(bug), `gotcha` (technically works, indefensible practice). Tier follows
the "Feedback on missed issues" scheme in `AGENTS.md`: Critical /
Worthwhile / Stylistic.

---

## 1. `extract_orders` never closes its file handle

- **Where:** `extract_orders()` — `open(path, "r")` with no `with` and no
  `.close()`.
- **Category:** correctness (resource leak).
- **Tier:** Worthwhile. Harmless for one call in a short-lived script;
  becomes a real handle-exhaustion risk if this function is called
  repeatedly in a longer-running process.
- **What a good fix looks like:** a `with open(...) as f:` block.

## 2. Five near-identical `transform_*` functions

- **Where:** `transform_electronics`, `transform_clothing`,
  `transform_home`, `transform_toys`, `transform_books`.
- **Category:** duplication / design smell.
- **Tier:** Critical. This is the headline smell of the exercise — same
  shape as the `FibonacciSequence`/`TriangleNumberSequence` duplication in
  `sequence.py`, just relocated to a filter+transform shape instead of a
  class hierarchy. Five bodies differing only in one string constant.
- **What a good fix looks like:** one function taking `category` as a
  parameter (`transform_by_category(rows, category)`), or — better,
  since all five are called together and unioned in `__main__` — a
  single pass that computes revenue for every row regardless of category
  and skips the per-category split entirely, since nothing downstream
  actually needs the category-specific lists separately.

## 3. Broad `except Exception: pass` in every transform function

- **Where:** inside each `transform_*`, around the `float(...)` casts.
- **Category:** correctness / observability.
- **Tier:** Worthwhile, bordering Critical if a candidate doesn't connect
  it to real-world impact: a malformed row (bad `quantity`/`unit_price`)
  is silently dropped with zero trace — no log, no count, no indication
  data went missing. In a real pipeline this is how silent data loss
  happens. Same anti-pattern the repo's `GUIDE.md` calls out for
  `raise Exception(...)`, mirrored on the catching side.
- **What a good fix looks like:** catch a specific exception
  (`ValueError`), and at minimum log/count what was skipped rather than
  discarding it invisibly.

## 4. `category_totals` recomputes each row's category sum by rescanning everything

- **Where:** `category_totals(rows)` — nested loop, `for row in rows: for
  other in rows: ...`.
- **Category:** performance.
- **Tier:** Critical. This is the direct ETL-domain analog of the
  Fibonacci "rebuild from scratch every call" lesson from the sequence
  exercise — O(n²) where a single accumulation pass (build a
  `{category: total}` dict once, then a second pass to attach it) is
  O(n). Worth watching whether the candidate makes this connection
  explicitly ("this is the same shape as..." is a strong signal of
  transferred understanding, not just pattern-matching this file alone).

## 5. `region_summary(rows, cache={})` — mutable default argument

- **Where:** function signature default.
- **Category:** gotcha (technically works, indefensible).
- **Tier:** Critical, and a genuine "gotcha" in the AGENTS.md sense — it
  produces correct-looking output on a single run, which is exactly why
  it's dangerous. The default dict is created once at function
  *definition* time and shared across every call for the life of the
  process; a second call (different data, a test suite calling it twice,
  a notebook re-running a cell) returns stale/merged results from the
  first call, silently. Classic Python pitfall — worth checking whether
  the candidate names it as such ("mutable default argument") rather
  than just vaguely distrusting the `cache={}`.
- **What a good fix looks like:** `cache=None`, then `if cache is None:
  cache = {}` inside the function.

## 6. `load_orders` opens a new SQLite connection per row

- **Where:** the `for row in rows:` loop inside `load_orders`.
- **Category:** performance.
- **Tier:** Critical for a pipeline explicitly meant to handle "very
  large" data fast (callback to the framing from the earlier Fibonacci
  conversation) — connection setup/teardown per row dominates runtime at
  any real scale. Should be one connection (or a small pool), opened
  once, with either `executemany` or an explicit transaction around the
  loop.

## 7. `load_orders` builds SQL via f-string interpolation

- **Where:** the `INSERT INTO orders ... VALUES (...)` built with an
  f-string embedding row values directly into the SQL text.
- **Category:** correctness + security (gotcha).
- **Tier:** Critical. Two distinct problems worth the candidate
  separating: (a) **security** — this is the textbook shape of a SQL
  injection vulnerability, even though today's values come from this
  script's own generator rather than untrusted input; the code doesn't
  know that, and the shape is what matters, not today's data source; (b)
  **correctness**, independent of any adversarial input — any string
  value containing a single quote (an apostrophe in a region/category
  name) breaks the query outright. Parameterised queries (`?`
  placeholders) fix both at once. Good candidates will name *both*
  angles, not just "SQL injection."

## 8. No idempotency — rerunning the script duplicates rows

- **Where:** `load_orders` / the overall `__main__` flow — there's no
  dedupe, upsert, or table-clear step.
- **Category:** correctness (gotcha, only visible by actually rerunning
  it — confirmed: running `python etl.py` twice takes the `orders` table
  from 2000 rows to 4000).
- **Tier:** Critical for a pipeline, Worthwhile as a "first pass"
  observation — this one is easy to miss from reading the code alone
  since nothing about a single run looks wrong; it only surfaces from
  either running it twice or explicitly reasoning about what happens on
  a rerun (a re-triggered Airflow task, a retried job, etc.). Whether the
  candidate raises this *without* being told to rerun the script is a
  good signal of "thinks about operational behaviour," not just
  "read the code."

## 9. Lower-tier / stylistic items (present, but not the point of the exercise)

- **Category:** stylistic/design preference.
- No logging (only `print`), no log levels — reasonable in a small
  script, worth naming as a limitation for anything longer-lived.
- Config constants (`DATA_DIR`, `REGIONS`, etc.) and logic live in the
  same module with no separation — fine here, a legitimate call to leave
  as-is for something this size.
- No type hints — stylistic, not load-bearing given the rest of the repo
  (`template.py` et al.) is similarly light on them.

Don't expect (or require) a candidate to raise all of #9 — these are
useful if they come up organically, not omissions worth penalising.
