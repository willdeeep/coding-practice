# Answer key — `quick-drills/`

Not for the user to read before completing their own critique of a given
drill. For the assistant's use during Gotchas / Missed-issues / Final
feedback only.

This folder is a different shape from the other exercises: each file is a
**single-issue, cold-read drill** meant to take under five minutes,
intended for rapid-cycle practice rather than a full multi-issue critique.
Treat each file as its own exercise instance under the parent `AGENTS.md`
process — orientation, the one issue, reasoning, close — rather than
expecting a prioritised list of several things per file. Don't reveal
which file maps to which issue before the user reads it cold; that's the
entire point of this folder.

Categories: `duplication` (design smell), `performance`, `correctness`
(bug), `gotcha` (technically works, indefensible). Tiers: Critical /
Worthwhile / Stylistic.

---

## drill_01_customer_orders.py — SQL injection

- **Issue:** `get_orders_for_customer` builds the query with an f-string
  splicing `customer_name` directly into the SQL text, instead of using a
  parameterized placeholder — despite the seed/insert code right above it
  in the same file correctly using `?` placeholders, which makes the
  contrast easy to miss on a fast read.
- **Category:** gotcha (security). **Tier:** Critical.
- **Fix:** `conn.execute("SELECT order_id, amount FROM orders WHERE customer_name = ?", (customer_name,))`.

## drill_02_product_prices.py — N+1 query pattern

- **Issue:** `get_prices` issues one `SELECT` per SKU in a loop instead of
  a single query filtering with `WHERE sku IN (...)`.
- **Category:** performance. **Tier:** Critical (one query round-trip per
  item instead of one total — the standard "N+1" shape).
- **Fix:** one query with `IN (...)`, built from placeholders matching the
  length of `skus`, then map results back into the `{sku: price}` dict
  (watch for SKUs with no match needing to still appear as `None`).
- Note: this file's SQL is correctly parameterized — don't let the user
  flag injection here, there isn't any; the issue is round-trip count.

## drill_03_product_tags.py — mutable default argument

- **Issue:** `def add_tag(product, tag, tags=[])` — the default list is
  created once at function-definition time and shared across every call
  that doesn't pass its own `tags`.
- **Category:** correctness (gotcha — classic Python pitfall).
  **Tier:** Critical.
- **Verified effect:** running it shows `p1` ends up with `['sale',
  'clearance']` even though "clearance" was only ever passed to the call
  that produced `p2` — both calls mutated the same shared list object.
- **Fix:** `tags=None`, then `if tags is None: tags = []` inside the body.

## drill_04_order_status.py — resource leak (unclosed connection)

- **Issue:** `get_status` opens a new `sqlite3.connect(db_path)` on every
  call and never closes it — no `conn.close()`, no context manager.
- **Category:** performance / resource management. **Tier:** Worthwhile.
  Invisible in a two-call demo; the problem is accumulation under real,
  repeated use (connection/file-handle exhaustion).
- **Fix:** close explicitly in a `finally`, or `with
  contextlib.closing(sqlite3.connect(db_path)) as conn:`. Note:
  `with sqlite3.connect(db_path) as conn:` alone does **not** close the
  connection — `sqlite3.Connection.__exit__` only commits/rolls back the
  transaction, unlike a file object's context manager. Worth flagging if
  the user proposes bare `with sqlite3.connect(...)` as "the" fix.

## drill_05_apply_discount.py — broad except masking a real bug (clean-cut bad case)

- **Issue:** `apply_discount` wraps a single arithmetic expression in
  `except Exception: return price` — not a batch-processing context,
  a single computation whose caller passed the wrong type.
- **Category:** correctness (gotcha). **Tier:** Critical.
- **Verified effect:** `apply_discount(100.0, "ten")` silently returns
  `100.0` (the *undiscounted* price) instead of raising the `TypeError`
  that would have revealed the caller passed a string where a number was
  expected. The bug is hidden, not fixed.
- **Important — contrast with `s3-ingest-pipeline-refactoring`:** that
  exercise's broad `except` in a batch loop was judged *legitimate* (one
  file failing shouldn't halt the whole run). This one is deliberately
  the other case: a single-item computation where swallowing the error
  changes the answer silently instead of protecting a batch. If the user
  flags broad-except here, that's correct — don't let a prior "broad
  except can be fine" lesson get over-applied to a case where it isn't.
- **Fix:** don't catch at all here (let the `TypeError` surface), or catch
  a specific expected exception type only.

## drill_06_orders_in_year.py — non-sargable predicate

- **Issue:** `WHERE strftime('%Y', order_date) = ?` wraps the column in a
  function, same underlying mechanism as `warehouse.py`'s
  `substr(sale_date, 1, 4)`, just a different function.
- **Category:** performance. **Tier:** Critical/Worthwhile depending on
  scale — same lesson, new surface, good check for whether the concept
  transferred rather than got memorized against one specific query.
- **Fix:** a real date range: `order_date >= ? AND order_date < ?` with
  `'2025-01-01'` / `'2026-01-01'` bounds.

## drill_07_warehouse_connection.py — hardcoded credentials

- **Issue:** `WAREHOUSE_CONFIG["password"]` is a plaintext secret in
  source.
- **Category:** gotcha (security). **Tier:** Critical.
- **Fix:** load from environment variables or a secrets manager; never
  commit literal credentials.

## drill_08_invoices_vs_payments.py — join fan-out

- **Issue:** joining `invoices` to `payments` on `customer_id` (not
  unique on either side) before aggregating produces every
  (invoice, payment) row-pair per customer.
- **Category:** correctness (gotcha). **Tier:** Critical — same family as
  `net_revenue_by_product` in `warehouse.py`.
- **Verified effect:** customer 1 (2 invoice rows × 3 payment rows = 6
  joined rows) reports `invoiced=450.0` (true: 150.0, ×3) and
  `paid=180.0` (true: 90.0, ×2). Customer 2 (1 invoice, 1 payment)
  reports correctly by coincidence — `(200.0, 200.0)` — which is exactly
  why this bug is dangerous: it doesn't always look wrong.
- **Fix:** aggregate `invoices` and `payments` independently by
  `customer_id` first (two CTEs/subqueries), then join the two aggregates.

## drill_09_export_role_policy.py — maximally permissive IAM policy

- **Issue:** `"Action": "*", "Resource": "*"` — not even scoped to a
  service, full account-admin-equivalent access.
- **Category:** gotcha (security). **Tier:** Critical — a step further
  than `s3-ingest-pipeline-refactoring`'s `s3:*`/`*`, worth noticing the
  user catches the *degree* of over-permissiveness, not just its presence.
- **Fix:** least-privilege — scope `Action` to the specific operations
  this role performs and `Resource` to the specific ARN(s) it needs.

## drill_10_webhook_events.py — idempotency

- **Issue:** `events` table has no primary key / unique constraint on
  `event_id`; `load_events` does a plain `INSERT` with no guard against
  redelivery.
- **Category:** correctness (gotcha). **Tier:** Critical — direct
  reinforcement of the `s3-ingest-pipeline-refactoring` lesson in a new
  domain (webhooks instead of S3 events), checking whether the concept
  generalizes past that one script.
- **Verified effect:** redelivering the same event produces
  `Total events stored: 2` instead of the correct `1`.
- **Fix:** `event_id TEXT PRIMARY KEY` in the schema, then
  `INSERT OR IGNORE` (or `OR REPLACE`) instead of plain `INSERT`.
