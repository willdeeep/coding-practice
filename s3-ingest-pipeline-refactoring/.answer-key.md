# Answer key — `ingest.py`

Not for the user to read before completing their own critique
(`AGENTS.md` Checkpoints 1–5, same convention as the other exercises).
For the assistant's use during Gotchas / Missed-issues / Final-feedback
only.

Categories: `duplication` (design smell), `performance`, `correctness`
(bug), `gotcha` (technically works, indefensible). Tiers: Critical /
Worthwhile / Stylistic.

---

## 1. Hardcoded AWS credentials (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`)

- **Category:** gotcha (security).
- **Tier:** Critical. Same class of issue as the Snowflake credentials in
  `warehouse.py` — plaintext secrets in source, this time specifically the
  kind that would grant real AWS account access if this constant were ever
  pointed at a real account instead of `moto`. Should come from the
  environment, an instance role, or a secrets manager — never hardcoded,
  even in code that "only" talks to a mock in training.

## 2. `INGEST_ROLE_POLICY` — `"Action": "s3:*", "Resource": "*"`

- **Category:** gotcha (security).
- **Tier:** Critical, and maps directly to "IAM" in the job spec. This
  role can read, write, delete, and change permissions on *every* bucket
  in the account, not just the one landing bucket it actually needs. The
  fix is least-privilege: `s3:GetObject`/`s3:ListBucket` scoped to the
  specific bucket ARN this pipeline actually reads from.

## 3. No idempotency — a redelivered event duplicates every row

- **Where:** `run_ingest` / `process_object` — nothing tracks which keys
  have already been loaded.
- **Category:** correctness (gotcha — the most important one in this
  exercise). S3 event notifications to Lambda are **at-least-once**
  delivery by design — AWS's own documentation is explicit that the same
  event can invoke a Lambda more than once, and a real production system
  must be idempotent to it, not treat redelivery as a rare edge case.
  Verified by literally re-running ingestion once in `__main__` to
  simulate exactly that: 3 files × 200 rows should be 600, but the actual
  total is **1200** — every row duplicated. Same underlying lesson as the
  no-idempotency issue in `orders-etl-refactoring/etl.py`, now in the
  specific, very real AWS context that makes it not just a rerun
  inconvenience but an expected production condition. Fix: track
  processed keys (a `processed_objects` table keyed on `source_key`,
  checked before loading) or make the load itself idempotent (delete
  existing rows for that `source_key` before inserting, or upsert on a
  natural key).

## 4. A new S3 client created per object, inside the loop

- **Where:** `process_object` calls `_client()` itself, and it's invoked
  once per key inside `run_ingest`'s loop.
- **Category:** performance.
- **Tier:** Worthwhile — same family as the "new DB connection per row"
  lesson from `orders-etl-refactoring`, one layer up the stack: client
  construction (credential resolution, connection pool setup) happening
  per object instead of once per run. With `moto` this is invisible; with
  a real client hitting real AWS, per-call client construction is exactly
  the kind of thing that shows up as latency at scale. Fix: build the
  client once in `run_ingest` and pass it into `process_object`.

## 5. Broad `except Exception` in `process_object` — nuanced, not a flat miss

- **Category:** correctness / observability — **judgement call, not an
  automatic critical**.
- **Tier:** Stylistic-to-Worthwhile. This is deliberately similar in shape
  to the batch-processing case the user's own `error-handling.md` already
  documents as a *legitimate* use of a broad `except` — "one item's
  failure shouldn't halt the batch" is genuinely the right call here; a
  malformed file three-quarters through a run shouldn't crash the whole
  ingest. **Don't reward a flat "broad except is bad" here** — a
  candidate who's actually internalised the earlier lesson should
  recognise this as one of the legitimate cases, not misapply the rule.
  The real, narrower gap: failures are `print`ed and silently dropped with
  no structured tracking (no count, no list of which keys failed and why,
  nothing surfaced to the caller) — compare to `extract_orders` in
  `etl_ref.py`, which returns `(valid_orders, failed_rows)` rather than
  just printing and moving on. That's the actual improvement worth
  looking for: keep the broad catch, add structured failure reporting.

## Lower-tier / stylistic

- `print` instead of `logging` — would matter more in real Lambda (though
  `print` output does reach CloudWatch Logs there, structured log levels
  and fields still don't come for free with it).
- No retry/backoff on the S3 calls themselves (separate from the
  idempotency issue in #3 — this is about transient S3 errors, not
  duplicate delivery).

Don't expect a candidate to raise every stylistic item — useful if they
come up organically, not omissions worth penalising.
